# Troubleshooting

If something isn't working, find your symptom below. Most issues fall into one of four buckets: **auth**, **connectivity**, **Node version**, or **transport mismatch**.

## Auth failures

Authentication is pass-through — the server forwards your `Authorization: Bearer <token>` to the hosted service and makes no auth decision itself. So an auth error almost always comes from upstream.

### Tool calls return `401`

The token is missing or expired. Check that your MCP client is actually sending an `Authorization: Bearer <token>` header (HTTP) or is configured to pass your token (stdio), and that the token is current. Refresh it in your client and retry.

**Validate the token first — neither of the following can produce a 401 on a Production Master tool call.** Two Claude Code 2.1.225 bugs cause 401s *elsewhere in the same session* and are easy to mistake for this one, so they are listed to be ruled out, not as an alternative diagnosis:

- On macOS, a timed-out keychain read could make an **MCP OAuth** server fail with a burst of 401s as if never authenticated. This server uses pass-through bearer auth, not MCP OAuth, so it is not in that path — but if OAuth-based servers registered in the same session are 401ing too, that shared symptom is the host bug, and updating Claude Code fixes those entries. It does not explain a 401 on a Production Master tool call, which still means the bearer header is missing, wrong, or expired.
- In headless (`claude -p`) runs, a transient 401 could replace a long-lived `CLAUDE_CODE_OAUTH_TOKEN` with a stored login's short-lived token, breaking the session until restart. That credential authenticates **Claude Code itself to Anthropic** — this server never sees it and never uses it. A CI job where the model's own requests start failing hit that bug; a CI job where only `production-master` tool calls 401 has a token problem, and the fix is to re-issue the bearer token and update the client configuration.

**Using `headersHelper` (Claude Code) and getting an OAuth prompt instead of a retry? Fixed in 2.1.248.** [Quick Start](quick-start.md) recommends `headersHelper` over a static `--header` bearer for minting short-lived tokens. Before 2.1.248, a `401` from this server on a `headersHelper`-minted `Authorization` header — the ordinary case of the minted token having expired — could make Claude Code fall into MCP OAuth discovery instead of just re-running your helper command for a fresh token. This server never implements MCP OAuth, so that path always dead-ends; it looks like the server "doesn't support" `headersHelper` when the real cause is the client mishandling the retry. On 2.1.248+, a `401` re-runs the helper and retries the call, matching the documented behavior. If a `headersHelper` setup that used to work suddenly starts prompting for OAuth sign-in, update Claude Code before switching back to a static bearer.

### Tool calls return `403`

The token is valid but your account lacks access to the requested operation on the hosted service. Confirm your account has the needed access; the server cannot grant it — authorization is decided upstream.

### The token seems to "not stick"

There is nothing to persist on the server side — it stores no credentials. If calls stop authenticating, the fix is always in what your client sends next; update the token in your client configuration.

## Connectivity

### The client can't reach the HTTP endpoint

For the Streamable HTTP transport the client posts to `<server-url>/mcp`. Verify the URL is the bare endpoint (no trailing slash issues), that it's reachable from your machine, and that any proxy or firewall allows the connection. A proxy that buffers or drops long-lived responses can interfere — try a direct connection to isolate it.

**Claude Code:** start with `claude mcp list` (or `/mcp` in a session). Since Claude Code 2.1.219 a failing server entry shows the HTTP status and error text of the failed connection — a `401` there points you at [auth](#auth-failures), a timeout or DNS error at the network path, and a `404` at a wrong endpoint URL. Claude Code also warns when an MCP config value carries hidden leading/trailing whitespace — a classic cause of an `Authorization` header that looks right but fails upstream. If you run Claude Code headless (`claude -p`), config entries that fail validation are skipped and reported in the init event's `mcp_server_errors` field, so a CI job can assert the server registered cleanly. One more headless gotcha with a version answer: before 2.1.221, servers passed via `--mcp-config` were not connected before the first turn in print mode, so a first-turn tool call could come out as literal text instead of a real call — if a CI transcript shows the model "writing" `production-master` tool calls as prose, update Claude Code to 2.1.221+ rather than debugging the server. Finally, if you probe the endpoint with `curl` from a **sandboxed** Claude Code session, a sandbox network denial used to look like a generic connection failure; since 2.1.224 the Bash tool result includes the sandbox violation details — which network (or file) access was denied and why — so you can tell sandbox policy apart from a real network problem before blaming the server or the proxy. One more symptom with a version answer: before 2.1.232, a server that failed to answer Claude Code's protocol-version probe — or answered it with a malformed reply (a proxy or captive portal returning HTML at `<server-url>/mcp` produces exactly this) — left the client **hanging for the full 30-second connect timeout** before reporting failure. On 2.1.232+ the failure surfaces immediately with error text in `claude mcp list`. If registering this server appears to hang for ~30 seconds and then fail, update Claude Code first; the immediate error you then get points at the real cause (usually a proxy rewriting the response or a wrong endpoint URL).

**Headless first turns can bound how long they wait on this server's stdio startup — `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` (Claude Code 2.1.274).** Running `production-master-mcp` over stdio in a `claude -p` / CI pipeline means the client spawns and initializes the server subprocess before the first turn can use its tools, and by default the client waits for that startup to finish. Claude Code 2.1.274 adds `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` to cap that wait. For a **tool-dependent one-shot job**, do not cap it at 15s or set it to `0`: a one-shot `-p` has no later turn, so the prompt can finish as if the tools were absent. Preinstall or cache the package, leave the wait unbounded (or set it high enough for a worst-case cold start), and assert registration (`claude mcp list` / the init event's `mcp_server_errors` field) before the prompt that needs these tools — see [Quick Start → stdio](quick-start.md#option-b--run-over-stdio-local). `0` (skip the wait) is only for jobs that do not need these tools on the first turn. This is a client-side timing knob, not something this server configures.

**An MCP entry configured as `type: "http"` that fell back to legacy HTTP+SSE negotiation could mishandle a 4xx (including a 422) from the server — fixed in 2.1.274.** This server only implements Streamable HTTP (no legacy SSE endpoint), and its `POST /mcp` answers a missing or malformed `Authorization` header with an ordinary 401 and a JSON body (see [Auth failures](#auth-failures)) before MCP itself ever starts. Before Claude Code 2.1.274, if an `http`-typed entry's negotiation fell back to the legacy HTTP+SSE transport and the server it reached answered with a 4xx or a 422, the client could mishandle that response instead of surfacing it as a normal connection or auth error — a case this server's own straightforward 401 could trigger on an older client purely through the fallback path, not through anything wrong with the response itself. On 2.1.274+ those status codes are handled correctly during legacy fallback too. Nothing changes here: the server's transport and status codes are unchanged: this was a client-side negotiation fix.

**Running this client via Amazon Bedrock, Google Vertex AI, or Microsoft Foundry? Claude Code 2.1.247 makes an MCP connection failure visible to the model, not just to you.** Before 2.1.247, if this server (or any MCP server) failed to connect in a Bedrock-, Vertex-, or Foundry-backed Claude Code session, that failure could stay purely a host-side signal — surfaced in `claude mcp list` / `/mcp` for you to see, but never told to Claude itself the way a direct-Anthropic-API session already was. That meant Claude could carry on a turn assuming the Production Master tools existed instead of naming the connection failure back to you. On Claude Code 2.1.247+, Claude is told when the MCP server fails to connect on these gateway-backed sessions too, so a failed registration shows up in the transcript as an acknowledged failure, not a silent gap in the tool list. This is a client-side diagnosability fix; the server's own connection behavior, error codes, and failure taxonomy (below) are unchanged. As of Claude Code 2.1.271, the same Foundry / Claude Platform on AWS sessions get a speed improvement too: if `production-master` is marked `alwaysLoad` in the client config and finishes connecting mid-conversation, its tools are usable on the very next turn instead of needing an extra tool-search round trip first. This repo's own [Quick Start](quick-start.md) examples don't set `alwaysLoad` (it's a client-side MCP config flag, not something this server requires), but if your deployment sets it for faster availability after a reconnect on one of these gateways, this is what changed. **As of Claude Code 2.1.274, the same Bedrock, Vertex, Foundry, and telemetry-disabled sessions default to MCP client v2** — the negotiation path every direct-Anthropic-API session already used, replacing v1/legacy negotiation as the default there. This is an internal protocol-client change with nothing for this server to support differently: it is a standard MCP server built on the official SDK and speaks whichever protocol version the connecting client negotiates. If a gateway-backed deployment sees a `production-master` regression right after upgrading to 2.1.274, `MCP_SDK_GENERATION=v1` or `MCP_PROTOCOL_NEGOTIATION=legacy` reverts the client to the previous negotiation while you investigate, but nothing about this server requires that fallback.

**If you operate this server behind a serverless runtime,** one more version answer, this time on the server-operator side rather than the client side: before 2.1.233, Claude Code could get stuck **endlessly reopening the MCP v2 subscriptions/listen stream** against a server hosted on a serverless platform, instead of settling after a normal reconnect. That reads as unexplained request-volume spikes, connection churn, or elevated invocation counts in the hosted platform's logs — not as anything the server did — and every client hitting it looks like a misbehaving integration. On Claude Code 2.1.233+ the reconnect settles normally. If you see this pattern from Claude Code clients specifically, ask them to update rather than changing the server's connection handling.

**Enterprise deployments using `strictPluginOnlyCustomization` or an MCP allow/deny list: a reconnect could evade the policy before 2.1.257.** `production-master` is registered as an ordinary settings-file MCP entry (via `claude mcp add`, not a bundled plugin — this repo ships no `.claude-plugin/` manifest), so if your organization keeps it out with `strictPluginOnlyCustomization` or an MCP allow/deny list, that policy is meant to hold for the life of the session. Before Claude Code 2.1.257, running `/mcp reconnect` or re-enabling a server from `/mcp` could still connect a settings-file entry that a managed allow/deny list — or `strictPluginOnlyCustomization` loaded after startup — was supposed to block, so a `production-master` registration your org intended to keep blocked could come back after a reconnect. On 2.1.257+, reconnect and enable both re-check the policy instead of trusting the entry's prior state. If a blocked `production-master` registration ever reappeared after a `/mcp reconnect` on an older client, that was the host bug, not a gap in this server's own auth — the server itself makes no admission decision either way; it only forwards whatever bearer the client sends once connected.

**`allowedMcpServers` changed scope in 2.1.259 — it no longer covers a `managedMcpServers` entry.** [Quick Start](quick-start.md) now documents `managedMcpServers` as an alternative to per-user `claude mcp add` for rolling `production-master` out org-wide. As of Claude Code 2.1.259, `allowedMcpServers` governs only user-added entries (`claude mcp add`, project `.mcp.json`) — a `managedMcpServers` entry loads regardless of what `allowedMcpServers` says. If your organization wants a `managedMcpServers`-deployed `production-master` to stay optional or blockable, use `deniedMcpServers` instead; `allowedMcpServers` alone no longer keeps it out. This is a Claude Code policy-scope change, not a change in how this server admits connections — it still makes no admission decision of its own either way.

**Headless (`claude -p`) or SDK sessions that never recover from a blip are a known bug fixed in 2.1.243.** Before 2.1.243, a remote MCP server connection (this server's Streamable HTTP transport included) that dropped mid-session in a non-interactive or SDK-driven Claude Code run could stay disconnected for the rest of that run instead of reconnecting — a CI job or agent pipeline would then see every later `production-master` tool call fail as if the server had gone down, even though a normal interactive session reconnects fine. As of 2.1.243, these sessions reconnect automatically or report the connection as failed instead of hanging in a broken state. If a headless or SDK integration against this server intermittently "loses" the tools partway through a run, update Claude Code before suspecting the server or its network path. As of 2.1.246, the same class of session also auto-continues a response that a server error, connection loss, or stall cut off mid-stream, instead of ending the run with a bare error — a further host-side reliability improvement for CI pipelines driving this server's tools, with nothing to change here.

**As of Claude Code 2.1.273, when reconnection finally gives up, you're told so instead of finding out from a failed call.** The 2.1.243/2.1.246 fixes above mean a `production-master` connection that drops mid-session reconnects automatically or ends the run cleanly — but on earlier clients, a reconnect attempt that keeps failing (the server genuinely down, a firewall rule change, `PM_API_URL` broken on the operator side) surfaced no differently than a slow network: you'd only notice once a tool call errored or the tool list emptied. On Claude Code 2.1.273+, once automatic reconnection to an MCP server gives up, Claude Code shows an explicit notification naming the server and pointing you at `/mcp`. This is host-side diagnosability only — the server has no reconnect logic of its own for the client to trigger, and its own disconnect/failure behavior (the `error` code table below) is unchanged — but it's the clearest signal yet that a `production-master` connection is genuinely down rather than merely slow, so start there before digging into the failure-code table.

**A long-running `production-master` call over Streamable HTTP could hit a hard client-side timeout of roughly five minutes — fixed in 2.1.274.** This server's HTTP transport ([`http.ts`](../../packages/mcp-server/src/http.ts)) is Streamable HTTP, and some investigation tool calls can legitimately take longer than a few seconds to come back from the hosted service. Before 2.1.274, Claude Code enforced an internal ceiling of about five minutes on a Streamable HTTP MCP tool call regardless of whether the server and upstream were still actively working, and reported the call as timed out at that mark even when nothing was actually stuck. On 2.1.274+ that ceiling is fixed, so a `production-master` call that genuinely needs longer than five minutes is no longer cut off by the client. If you were previously working around this — splitting a call, polling a long investigation in smaller steps, or avoiding the HTTP transport in favor of stdio for slow calls — that workaround is no longer necessary once you're on 2.1.274+; the server's own behavior for a slow upstream call (it simply awaits the response, see `requestUpstream` in `upstream.ts`) has not changed.

**A `production-master` tool call that "succeeded with nothing" in a headless/CI run may have actually been interrupted — fixed in 2.1.246.** Before 2.1.246, an MCP tool call cut off mid-flight by an incoming message in a headless or remote session could be reported to the client as "completed with no output," which reads exactly like a legitimate empty result (for example an investigation with genuinely no actions). That ambiguity is precisely what this server's own relay refuses to produce on its own side — an upstream failure is never returned as an empty-but-successful tool result, see the failure-code table below — but a pre-2.1.246 client could still manufacture that same false signal itself when a call was interrupted rather than genuinely empty. On Claude Code 2.1.246+, an interrupted tool call is reported as an explicit interrupted error instead. If a headless run against this server shows a `production-master` call that "finished empty" in a way that doesn't match what you expect the hosted service to return, update Claude Code before assuming the investigation, action, or resource really is empty.

### Claude replies "your message came through empty" right after a tool call

Before Claude Code 2.1.268, Claude could occasionally reply that your message came
through empty immediately after any MCP tool call completed — a host-side rendering
bug with no relation to what the tool actually returned. A `production-master` call
that succeeded (or failed with one of the `error` codes below) could still be
followed by this message, which reads like the server sent back something broken. It
didn't: the server's own relay never fabricates a response, and this bug fires
after the tool result is already in hand, regardless of which MCP server produced
it. On Claude Code 2.1.268+ this no longer happens. If you're on an older client and
hit it, just resend your message — retrying the tool call itself is not necessary.

### Calls reach the server but fail upstream

If the server is reachable but tool calls fail, the failure happened between the server and the hosted service. Every such failure comes back as a tool error with a specific `error` code, so you can tell the causes apart instead of guessing — and none of them is ever reported as an empty-but-successful result:

| `error` | Means | What to do |
|---|---|---|
| `upstream_unauthorized` | The hosted service rejected your token (HTTP 401). | Mint a fresh token; check the client is sending the one you think it is. |
| `upstream_forbidden` | The token is valid but lacks scope for that call (HTTP 403). | Check the token's scope for the investigation you're addressing. |
| `upstream_not_found` | The hosted service has no such investigation or resource (HTTP 404). | Check the `investigationId`. |
| `upstream_rate_limited` | You are being throttled (HTTP 429). | Back off and retry. |
| `upstream_failed` | The hosted service returned some other non-2xx. | The `message` carries the service's own detail. |
| `upstream_unreachable` | The server could not open a connection at all (DNS, refused, timeout). | Check `PM_API_URL` and network egress from wherever the server runs. |
| `upstream_invalid_response` | A 2xx whose body was not valid JSON — usually a proxy or captive portal answering instead of the API. | Check `PM_API_URL` points at the API, not a gateway. |
| `relay_error` | The server itself threw while relaying. | Report it (see below); include the `message`. |

An `upstream_*` error's `message` may quote the hosted service's own error body to keep the failure diagnosable. Your bearer token is stripped out of that text before you ever see it — if the upstream ever echoed your `Authorization` header back into an error, it reaches you as `[redacted]`. The server also never writes the token to its logs; server logs record a failed request's method and path only, never its headers.

## Node version

The server targets **Node.js 22** (pinned in `.nvmrc`). If the server fails to start — especially over stdio, where your client launches it via `npx` — confirm Node 22 is installed and on `PATH`. Run `node --version`; if it isn't 22, `nvm use` in the repo or install Node 22.

## Transport mismatch

The server speaks two transports and they are not interchangeable in a single client entry:

- **Streamable HTTP** — the client connects to a running server at `<server-url>/mcp`. Use this for a hosted/remote server. The client entry needs a **URL** (and a bearer header), not a launch command.
- **stdio** — the client launches the server as a local subprocess and talks over standard I/O. The client entry needs a **command** (e.g. `npx …`), not a URL.

If your client "connects but sees no tools" or "fails to start," the usual cause is configuring one transport's shape (URL vs command) against the other. Match the entry to the transport you intend to use — see [Quick Start](quick-start.md).

**Claude Code:** one more "connected but no tools" case with a version answer. Before 2.1.224, an MCP server that finished connecting **mid-turn** — e.g. added or reconnected while the model was already working — could have its tools deferred for tool search without their names ever being announced to the model: the connection succeeds and `/mcp` lists the server, but the model acts as if the Production Master tools don't exist. This looks exactly like a server-side tool-listing bug and isn't one. On Claude Code 2.1.224+ mid-turn connections announce their tools correctly — if you hit this symptom, update Claude Code rather than re-registering or debugging the server.

**A third "connected but no tools" case, fixed in 2.1.259: a server that disconnects mid-listing used to look connected anyway.** Before 2.1.259, if `production-master` dropped its connection while Claude Code was still in the middle of listing its tools (a network blip during startup, a restart timed badly), the client could be left showing the server as connected in `/mcp` with an empty tool list, instead of reporting it as disconnected or retrying. That reads exactly like the mid-turn case above and like a server bug, but isn't one either — the server's own tool listing is unconditional (see [Commands](reference/commands.md#tools)) and returns the full set on every successful connection. On Claude Code 2.1.259+, a disconnect during tool listing surfaces as a disconnected state instead. If `production-master` ever shows connected with zero tools right after startup or a reconnect, update Claude Code before suspecting the server.

**A fourth case, not "no tools" but "the right tool, unresolved" — fixed in 2.1.271.** This server registers all 20 `investigation.*` tools under their full wire name (`mcp__production-master__investigation.*`, via `wireToolName` in `register-tools.ts`), which is exactly the shape Claude Code's tool search (deferred tool loading) expects. Before 2.1.271, if Claude tried to call one of them by its short contract name (e.g. `investigation.start`) instead of the full `mcp__production-master__investigation.start`, tool search could return no match — the server is connected, `/mcp` lists the tool, but the call itself fails to resolve, which looks like a missing or misnamed tool on the server side. It isn't: the server's tool set and wire names never changed, and a call that does reach the server always resolves — this was purely the client failing to map a bare name back to the full one during tool search. On Claude Code 2.1.271+, tool search resolves a bare name correctly. If a `production-master` tool call errors as "not found" despite the tool being listed, update Claude Code before renaming or duplicating tools here.

## Still stuck?

Open a GitHub issue with your MCP client and version, the transport you used (HTTP or stdio), the server version, and the redacted output or log excerpt. Never include tokens or service credentials.

**Claude Code:** before 2.1.234, Claude Code's own MCP diagnostic output could leak secrets from a session. That was a host-side bug in Claude Code's diagnostics, not this server logging anything — the pass-through design already never logs the forwarded bearer token, on any version — but if you're on Claude Code 2.1.234+, pasting `claude mcp list` output or a session transcript into an issue is safer than it used to be. Redacting before you share is still the rule above, not a version-gated exception. As of 2.1.257, that same hygiene extends to Claude Code's own MCP connection and OAuth debug/error logs: credentials carried in a server's URL or request headers are now redacted there too. This server has no OAuth credentials of its own (pass-through bearer only), but if you ever capture a verbose or `--mcp-debug` log while connecting to `production-master` for a bug report, a log taken on 2.1.257+ redacts the bearer from that client-side view as well as from `claude mcp list`/transcript output — on top of, never instead of, this server's own never-log-the-token design (`scrubToken` in `upstream.ts`). Still redact before you share; the fix narrows what a log can leak by accident, it doesn't make sharing an unredacted one a rule you can skip.

**Cursor:** if the server shows as connected in Customize / MCP but the model never calls Production Master tools, confirm the entry is the HTTP shape (`url` + `Authorization` header) rather than a stdio `command`, and that the bearer token is current. Team-distributed Team MCPs (Cursor 3.10+) use the same pass-through auth — a stale team-installed token fails the same way as a hand-edited `mcp.json`.
